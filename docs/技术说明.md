# 技术说明

面向想改规则 / 修 bug / 适配新版本的人。不涉及业务背景，只讲"为什么这么写"。

---

## 1. 为什么不能用全局字符串替换

最直观的做法是 `content.replaceAll("Accept", "接受")`。它能用，但有三类致命问题：

1. **命中代码**。`"Accept"` 可能同时是 `type==="Accept"` 的协议值，替换后分支永远不成立。
2. **命中标识符**。压缩后的 bundle 里有
   `Object.defineProperty(nn,"Name",{get:()=>Hh.Name})` —— 这里的 `"Name"` 是 **ES 模块导出名**。
   把它翻成 `"名称"`，模块就不再导出 `Name`，`new t.Name(...)` 抛
   `TypeError: t.Name is not a constructor`，扩展激活失败、面板一直转圈。
3. **随版本失效**。旧汉化包把压缩变量名写进匹配串（`k71="Set model to "`），
   新版本一改变量名，规则全部失配。

所以本项目只做**有证据的精确改写**：先证明某个字面量是展示文本，再改它的内容，别的一律不动。

## 2. 词法层：为什么要自己写

用正则扫字符串字面量在 6MB 压缩 bundle 上必然出错：
正则字面量里可以出现引号（`/["']/`）、模板字符串里可以嵌套模板（`` `${a?`${b}`:""}` ``）、
字符串里可以出现 `//`。任一处判断错，后面所有位置全部错位。

`lib/lexer.js` 是一个手写词法器，处理：

- `'…'` / `"…"` 字符串（含转义）
- `` `…` `` 模板字符串，**含 `${}` 里嵌套的模板与字符串**（递归 `scanExpr` / `scanTemplate`）
- 正则字面量（用"前一个有效 token"判断除法还是正则）
- `//` 与 `/* */` 注释
- Unicode 标识符

自检指标：2.1.329 两个 bundle 共 **3,137,000+ token**，token 区间**0 重叠**，
所有 string/template token 的首尾引号**0 异常**。

## 3. 规划层：什么算"界面文案"

一个字面量出现位置，满足下列任一"界面锚点"即视为展示文本：

| 锚点 | 例子 |
|---|---|
| UI 属性值 | `children:"Cancel"`、`title:"Close preview (Esc)"`、`placeholder:"Filter commands…"` |
| 宿主 API 实参 | `showInformationMessage("Failed to restart Claude: …")`、`showQuickPick([...])` |
| 三元 / 逻辑分支 | `return ok ? "Saved" : "Failed"`、`x = c ? "A" : "B"` |
| 标签字典值 | `{cwd:"Working folder", "Peer address":"Messaging address"}` |
| 枚举标签映射 | `{open:"Open", closed:"Closed"}`、`{working:"Working", finished:"Finished"}` |
| 变量型标签 | `var A="Status"` 且 `A` 之后出现在 `label:A` / `children:A` |
| 已定译文案 | 词库里人工复核过的句子，在所有"非比较/非键"位置一致替换（避免同一句话一半中文一半英文） |

"枚举标签映射"的判定：对象字面量里 **键是小写标识符、值是首字母大写或含空格的短语**，
且这样的键值对 ≥ 2 组。这条规则专门捞 `{open:"Open"}` 这类**键是协议值、值才是文案**的映射。

## 4. 排除层：改了一定出事的位置

按优先级，遇到即放弃该次出现：

1. 比较运算两侧（`===` `!==` `==` `!=` `<=` `>=`）
2. `case "…":`
3. `.includes("…")` / `.startsWith(` / `.indexOf(` / `.match(` / `.test(` …
4. 对象键（`{ "k": v }` 的 `k`）
5. 成员访问基址（`"x".foo`、`"x"?.["y"]`）
6. **名称位置**（`lib/namepos.js`）：
   - `Object.defineProperty(obj, "Name", …)` / `getOwnPropertyDescriptor` 的第 2 个实参 → 导出名
   - `obj["x"]`、`obj?.["x"]` → 计算成员
   - `"x" in obj`
   - `["A","B","C"]` 这类**名字列表**数组（兄弟元素 ≥ 60% 是单 token 标识符）
7. 不含空白的单词串：除非处在"界面属性值 / 界面 API 实参 / 枚举标签映射 / 变量标签 / 白名单"，
   且**没有在全文任何地方被当作比较值**。

第 6、7 条是事故换来的。词法层能保证位置精确，但"这个字符串是不是同时被当标识符用"
只能靠这类结构检测；检测不出来时，宁可漏译，不可改坏。

## 5. 归一化层：抗压缩变量名变动

新版本打包器会整体重命名变量。若词条键是带变量名的原文，就会整批失配。

做法：把词条里每个 `${...}` 替换成哨兵 `\u0000`，得到"结构键"：

```
`${Je} may already be at the latest version; …`
`${Ke} may already be at the latest version; …`
        ↓ 归一化
`\u0000 may already be at the latest version; …`   ← 同一个键
```

命中后把**当前版本的** `${...}` 按顺序回填进译文。仅当源串与译文的插值数量一致时才建立
归一化条目（保证可以按序回填）；否则只保留精确匹配。

构建产物：`data/dict-norm.json`（`tools/build.js` 生成）。

## 6. 自证层：为什么"看起来对了"不算对

静态检查再细，也可能漏掉语义破坏（`"Name"` 就是）。因此有两条独立门禁：

**结构自证**（每次写盘前）：替换后重新词法分析，要求

- token 总数不变
- 每个位置的 token 类型不变
- 只有"计划内的位置"取值发生变化

任一不满足 → 抛错、整体放弃、不写盘（不会留下半汉化状态）。

**运行时冒烟**（`tools/selftest.js`，发布前必跑）：在真实安装上执行
`英文原文 → 应用 → 断言 → 还原 → 断言 → 再应用`，11 项断言，其中包括

- 还原结果与英文基线**逐字节一致**
- 重复应用结果不变（幂等）
- `package.json` 仍是合法 JSON
- 汉化后 `new Function(src)` 可解析

更进一步的做法（本仓库开发时用过）是把英文原文与汉化后内容分别加载进
**vscode 桩件 / DOM 桩件**，要求两者行为一致（都加载成功，或抛同一个错误）。
`webview/index.js` 在 DOM 桩件下能做到"两边都加载成功"；`extension.js` 受限于桩件完备度，
目前是"两边同错"——只要错误信息一致，就说明汉化没有引入新错误。

## 7. 快照：为什么不在仓库里放英文原文

- **合规**：仓库只放译文与工具，不放 Anthropic 的代码或二进制。
- **必要**：还原与幂等重打都需要"这个版本的英文原文"。做法是首次应用时把用户本机的
  英文文件复制到扩展 `globalStorage/baseline/<version>/`，并写 `manifest.json`
  （含每个文件的 SHA-256）。
- **防污染**：若当前文件已被别的汉化包改过（中文超过阈值），会先用 `zh→en` 反查还原，
  再用"正向重打是否与磁盘逐字节一致"做往返自证；反推不可靠时明确拒绝，而不是把中文固化成基线。

## 8. 已知局限

1. `package.json` 的 `contributes` 只在**重载窗口**后才被 VS Code 重新读取，所以改完必须重载。
2. 单词型标签需要人工加入 `data/i18n-labels.json` 白名单——这是刻意的保守设计。
3. 内嵌 Monaco 编辑器与 KaTeX 的文案不处理（见 `data/i18n-outofscope.json`）。
4. 发送给模型的提示词/工具协议不处理：翻译会改变模型行为。
5. 版本适配是"尽力而为"：未登记版本仍可应用，但新增文案会保持英文，需跑 `tools/audit.js` 补齐。

## 9. 开放问题：宿主侧改动撞上 zod 的运行时代码生成

**症状**：应用汉化后扩展激活失败，面板一直转圈。`Claude VSCode` 输出通道：

```
Activation failed: SyntaxError (<string(17)>)
    at new Function (<anonymous>)
    at wG.compile (extension.js:67:229)
    at e._zod.parse (extension.js:120:332)
    at _Re (extension.js:169:7090)
    at m6.getPanelTabSessions (extension.js:198:19938)
```

**已知事实**

1. zod 4 的 `Exec.compile()`（约 `extension.js:67`）会把源码片段拼起来交给 `new Function(...)`。
   报错发生在**编译期**而非校验失败，说明生成出来的源码本身语法非法。
2. 触发路径是 `getPanelTabSessions` → 解析持久化的会话标签状态（`ZodArray.safeParse`）。
3. 第一次全量改写宿主（546 处）**没有**此问题；扩到 580 处后出现。
   嫌疑集中在新加的那 34 处宿主替换（`data/i18n-gap-2.1.329*.json` 里的宿主条目）。
4. webview 侧从未复现 → 与 `new Function` 代码生成无关。

**当前规避**：`data/scope.json` 把宿主侧限制为 `allowKinds: ["api"]`
（只翻 `vscode.window.*` 实参），宿主替换 580 → 35 处，激活路径不受影响。

**下一步（按性价比排序）**

1. **二分定位那一条**：把 `data/scope.json` 的 host 改回 `{"allowKinds": null}`，
   再把 `i18n-gap-2.1.329*.json` 的宿主条目按批（每批 8~10 条）装入，
   每批重载窗口验一次。这比读 zod 内部实现快得多。
2. **静态缩小**：候选是「同时出现在 schema 构造实参里」的字符串。
   工作区已有探针 `zhcn-full/tools/probe_zod_enum.js`（callee 识别还粗，需改进）。
3. **彻底解法**：宿主侧改成白名单式——只翻 `vscode.window.*`、`registerCommand` 标题、
   状态栏文本、`withProgress` 标题，并把覆盖率写成明确数字。会损失一部分通知文案，但可证安全。
4. **测试缺口**：`tools/selftest.js` 只验文件层面（幂等、逐字节还原、语法可解析），
   **验不到运行时激活**。要自动化，需要一个更完整的 vscode 桩件
   （`workspace.fs`、`globalState`、`ExtensionContext`、`WebviewPanel`），把 `activate()` 真正跑到底。
   这是目前最大的测试缺口。

**给下一任的硬规矩**：宿主侧每扩一次范围，都要**真机重载验证**，不要只信 `selftest.js`。
